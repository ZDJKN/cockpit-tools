# 企业 Codex 账号池助手结课作业交付设计

## 目标

把已经验证通过的 Mock MVP 整理成一份可直接提交的完整 AI 产品结课作业。交付必须同时包含完整产品方案、可核验 Demo、项目复盘和 zip 压缩包。

## 产品边界

- 产品名称：企业 Codex 账号池助手。
- 面向企业内部需要使用 Codex 的 Windows 员工和账号管理员。
- 当前 Demo 只验证账号池调度，不接入真实钉钉 OAuth、真实 ChatGPT/Codex 凭据或 Windows Credential Manager。
- AI 在当前阶段表现为可解释的规则决策引擎：监测 Hourly/Weekly 额度、识别低额度风险、推荐换号并把最终决定交给用户确认。
- 文档必须明确区分“已实现的 Mock MVP”和“生产化规划”，不把未来能力写成已完成能力。

## 交付结构

最终目录包含：

1. `企业Codex账号池助手-AI产品完整方案.md`
2. `企业Codex账号池助手-AI产品完整方案.docx`
3. `企业Codex账号池助手-AI产品完整方案.pdf`
4. `README-如何体验Demo.md`
5. `项目复盘.md`
6. `Demo截图/`，包含客户端原型、后端模拟控制台和关键流程截图。
7. `源码/`，包含两个仓库的 Git 归档文件，不包含 node_modules、数据库、密钥或临时文件。
8. 最终 `企业Codex账号池助手-结课作业.zip`。

## 文档结构

主方案按课程要求组织为七章：产品基本信息、需求来源、产品方案设计、AI 工作流程、Demo 展示、预期收益、项目复盘。附录提供体验步骤、验证结果和安全边界。

DOCX/PDF 使用 narrative_proposal 预设和 editorial_cover 首页。正文采用清晰的章节层级、少量真正用于比较的表格、核心交互流程图和 Demo 截图。PDF 由最终 DOCX 渲染生成，二者内容一致。

## Demo 证据

- 服务健康：`GET /api/health` 返回 `{ok:true, mode:"mock"}`。
- 自动测试：后端 19 项、客户端 11 项通过。
- 演示脚本：验证三账号排他租约、五设备 FIFO、低于 10% 提示、用户确认和自动补位。
- 页面证据：客户端 `127.0.0.1:1420`，后端控制台 `127.0.0.1:4174`。

## 验收标准

- 七项课程要求在主文档中都有明确章节。
- 所有“已完成”陈述均有代码、测试、运行状态或截图证据。
- DOCX 每页完成 PNG 视觉检查，无裁切、重叠、乱码或异常分页。
- PDF 每页完成 PNG 视觉检查。
- zip 可正常解压，文件清单完整，且不包含 `.env`、token、SQLite 数据、node_modules 或 Git 历史目录。
